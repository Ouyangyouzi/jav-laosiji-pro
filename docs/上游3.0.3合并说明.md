## 一、先说结论：为什么不能"整份替换式"合并

我做了完整的三方比对（基线 3.0.0.2 / 你的 v0.1 / 上游 3.0.3），得到两个硬事实：

**1）上游 3.0.3 是整份重新压缩的产物，几乎所有内部标识符都换了名。**

| 基线 3.0.0.2 | 上游 3.0.3 |
| --- | --- |
| `const li="3.0.0.2"` | `const di="3.0.3"` |
| `vo=`、`El=86`、`_l=100` | `xo=`、`ql=86`、`Pl=100` |
| `Mi`、`vr`、`Ro` | `Ii`、`yr`、`Do` |
| `Ie`（115/移动端策略对象） | 在多个模块里改名为 `ze` |
| `we`（115 接口对象） | 在多个模块里改名为 `ke` |

**2）字节级三方合并（git merge-file）会产出 24 处冲突；而两种"整份取舍"的合并都直接语法报错。**

实测证据：

- 取"上游优先"→ `SyntaxError: Identifier 'De' has already been declared`
- 取"你的代码优先"→ 同样 `Identifier 'De' has already been declared`

原因很简单：合并结果里一半代码用旧名、一半用新名，旧名与新名在同一个作用域里重复声明。**这不是我合并得不够细，而是"重压缩构建产物"本身无法做文本级合并。**

**3）但好消息是：154 个上游 hunk 里，127 个是纯改名噪音，行为零变化，根本不需要移植。**

按骨架（标识符归一化后）比对，只有 **27 个 hunk 是真正的语义改动**。所以"合并上游更新"这件事，真正的工程量在 27 项，而不是 1.24 MB。

## 四、上游 3.0.3 真正改了什么（27 项语义改动）

按内容归类：

**A. 移动端样式（6 项）** → 本次已全部并入 v0.2。

**B. 「按模板整理」不再强依赖 JavDB（核心功能改动）**

文案变化最能说明问题：

| 基线 3.0.0.2 | 3.0.3 |
| --- | --- |
| 没认出番号、或 **JavDB 查不到**，保持原样 | 没认出番号、或 **模板所需资料不足**，保持原样 |
| 未查到，**使用 Sukebei 页面资料** | 没查到，**模板里的演员/片商等字段会是空的** |
| 主资料，Sukebei 页面补齐 | **已用 JavBus 补齐页面缺少的资料** |
| 按模板整理查 JavDB 失败 | **资料查询失败 / 请求失败 / 查询失败** 分类提示 |

即：整理时若 JavDB 缺演员/片商等字段，改为**回退页面资料 + JavBus 补齐**，并把失败原因细分。这正好压在你改过的整理链路上（冲突 18/19/20/22），**必须重写，不能文本粘贴**。

**C. 其它文案/字段（若干）**：新增「商品ID」「販売日」「云加速」「全部缓存」「已清理」「男演员」「安全验证」等词条，属 DMM/FC2 字段与提示细化。

**D. 127 个纯改名 hunk**：零行为变化，**无需处理**，这也是为什么"没有整份覆盖"并不等于"漏了功能"。
